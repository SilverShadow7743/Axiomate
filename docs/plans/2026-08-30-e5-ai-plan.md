# E5 implementation plan — AI

Follows `2026-08-30-e5-ai-design.md` (approved). Ordering principle: the pure payload
builders and the hostile-output checks land scenario-proven before any route or button
exists; the engine config change — the one step that touches the live AI path — lands alone
with its fallback chain pinned; UI and the deploy come last. **This phase has NO migration,
NO new reducer arms, and therefore NO persistSteps or persistence-proof work — stated here
so nobody hunts for it.**

Standing gates per step: `npx tsc --noEmit` → `npm run validate:scenarios` (183 now; **186**
after commit 1) → `npm run build`. The four audits (tenancy 33, persistence 71, attribution
3/3, discussion 11) run ONCE before the deploy as regression, not per step. Staged foreground
deploy; `data/validation.json` rides the scenario commit; splices via temp file + python.

Design constraints quoted: "the client builds every payload from the reader's own redacted
state"; "model output is untrusted input, checked twice by one rule"; "at `suggest` the
affordance is absent"; "the offline command palette is the permanent fallback"; the key is
"the USER's one manual step".

Substrate facts (verified): `app/api/chat/route.ts` — `const MODEL = 'claude-opus-5'` (line
45), key check at 168 with `offlineReply` fallback, `parseConfig` reads the posted
`ChatConfig` slice (terms/parties/workTypes/autonomy) with field-by-field fallbacks and the
fail-closed autonomy default. `lib/chat.ts` — `validateCreate`/`validateUpdate` are the
gates (322/281), `canPropose(cfg)` (137), `CreateProposal` (64), `offlineReply` (578).
`components/IssueWorkspace.tsx` — `resolveAutonomy(state.model, 'AGENT_WORKSPACE_ASSISTANT',
scopeChainOf(...))` yields `assistantOffered`/`assistantAutonomy` (~850); ChatPanel's
`onApply={applyProposal}` (2598) is THE apply path.

## Step 1 — the pure payload builders, scenario-proven (commit 1)

**Files:** `lib/assist.ts` (new), `scripts/scenario-validation.ts`, `data/validation.json`.

- `narrationFigures(state, today)` — the projection the model gets shown: portfolio
  concerns (`concernsFor`), forecast verdicts for open records carrying an estimate and a
  date (`forecastFor`), health/overdue/blocked counts, availability headlines for allocated
  people (the engine, meetings included). Built from `WorkspaceState` exactly as a READER
  holds it; never touches `state.rates`, commitment `reason` fields, or anything
  `clientView` empties.
- `suggestRequest(messages, scope)` — the thread→work payload: deleted stubs excluded,
  per-message and total caps (`MAX_INDEX_ROWS`'s spirit: bounded, stated), scope context
  (kind, id, title/name).
- **E5A** — the redaction net: a fixture state with SENTINEL values planted (a rate amount
  `77123.45`, a leave reason `SENTINEL-REASON-X`, a client-invisible note string) →
  `JSON.stringify(narrationFigures(...))` contains none of them, while containing the
  concern phrases and forecast sentences it exists to carry.
- **E5B** — hostile outputs against the EXISTING gate: `validateCreate` refuses an unknown
  status, an unknown work type (when the registry constrains), forged extra keys surviving
  into the applied action, and oversized strings. If a case E5B needs is not refused, the
  gate is extended DELIBERATELY and the new edge pinned — the design's second send-back
  clause governs.
- **E5C** — `suggestRequest`: stub exclusion, cap truncation stated in the result (never
  silent), scope fields present.

**Verify:** `npm run validate:scenarios` → **186 scenarios, 0 FAIL**; `npx tsc --noEmit`.
**Commit 1** with `data/validation.json`.

## Step 2 — the engine config (commit 2; the risk step, see below)

**Files:** `lib/config.ts`, `lib/chat.ts`, `components/ConfigWorkspace.tsx`,
`components/IssueWorkspace.tsx`, `app/api/chat/route.ts`.

- The `AgentDef` for the assistant gains an optional `modelId?: string` (or, if `AgentDef`
  rows are wholesale-seeded and awkward to extend, a sibling config field beside where
  `resolveAutonomy` reads — decide at the keyboard; the requirement is: registry-editable,
  seeded absent, ConfigWorkspace's agent-registry section shows it for the assistant row
  with placeholder `claude-sonnet-5`).
- `ChatConfig` gains `modelId?: string`; `parseConfig` reads it with the same
  field-by-field tolerance (absent → undefined, non-string → undefined).
  `IssueWorkspace`'s ChatPanel config block (~2595) posts it.
- The route: `const model = config.modelId ?? 'claude-sonnet-5'` replaces the constant at
  every use (lines 45/262/288/427 areas). **The fallback chain is the whole point: a stale
  browser mirror posting no modelId must land on `claude-sonnet-5`, never on a crash or a
  400.** The offline path does not read the model at all — its indifference is the second
  guard.

**Verify:** `npx tsc --noEmit`; `npm run validate:scenarios` (186 — the offline palette's
scenarios must not move); `npm run build`; grep proves the constant is gone:
`grep -n "claude-opus-5" app/api/chat/route.ts` returns nothing. **Commit 2.**

## Step 3 — `/api/assist` (commit 3)

**Files:** `app/api/assist/route.ts` (new).

POST only, two kinds. Session gate copied verbatim from the chat route (`getSession` +
`identityEstablished` → 401 "Sign in to use the assistant."); **no tenant resolution — the
route reads no server state, exactly like the chat route, and that statelessness is the
posture, not an omission.** No key → `{ offline: true, error: 'The assistant is offline — no
model key is configured.' }` with status 200 — a configuration fact, not an error. Body
caps mirror the chat route's parse (bounded messages/figures, 400 in words on malformed).

- `narrate`: figures payload → one Messages call (the configured model, same fallback
  chain, MAX_TOKENS-scale cap) → `{ prose }`.
- `suggest-work`: `suggestRequest` payload → one call asking for a `CreateProposal`-shaped
  JSON → **`validateCreate` runs server-side before the response leaves** (the same gate the
  client will run again) → `{ proposal }` or the refusal in words.

**Verify:** `npx tsc --noEmit`; `npm run build` (route listed); local
`curl -s -X POST .../api/assist -d '{"kind":"narrate"}'` on the dev server answers the
offline JSON (no key locally beyond .env — verify which env the dev shell carries and use
the offline assertion accordingly). **Commit 3.**

## Step 4 — the two buttons (commit 4)

**Files:** `components/PortfolioPanel.tsx`, `components/DiscussionTab.tsx`,
`components/IssueWorkspace.tsx` (prop threading only if needed).

- **Portfolio**: "Narrate this" in the panel header → `narrationFigures` from the reader's
  own state → POST → prose inline under "AI-written; the figures above are the source", with
  the offline answer rendered as a plain sentence. The button never disables silently.
- **Discussion**: "Suggest a work item" in `DiscussionTab`'s header, rendered only when
  the thread has live messages AND autonomy allows proposals — reuse the EXISTING
  resolution: thread the `assistantAutonomy` value (or `canPropose` over the posted config)
  from `IssueWorkspace`; do not invent a third check. Click → `suggestRequest` from the
  messages already fetched (reader-gated by `/api/discussion`) → POST → client re-runs
  `validateCreate` → card with title/type/severity/description and **Apply | Dismiss**.
  Apply routes through the SAME `applyProposal` path ChatPanel uses (thread the callback or
  lift the card into IssueWorkspace — whichever keeps `applyProposal` the single apply
  path), with the parent resolved as: project thread → that project node id; issue thread →
  the issue's own `parentId`. Validation, History and attribution are then identical to a
  hand-created record by construction.

**Verify:** `npx tsc --noEmit`; `npm run validate:scenarios` (186, untouched);
`npm run build`. **Commit 4.**

`npm run audit:tenancy` (33) · `audit:persistence` (71) · `audit:attribution` (3/3) ·
`audit:discussion` (11) — all unchanged. Then the staged foreground recipe (archive → ci →
generate → build → package → `migrate status` "up to date" → `az webapp deploy` →

Live, in Chrome, WITHOUT a key (production has none):
1. The chat assistant still answers in palette mode — the permanent fallback holding.
2. Portfolio → "Narrate this" → the honest offline sentence, not an error state.
3. A Discussion thread → "Suggest a work item" visible at `propose`+ autonomy; flip the
   registry's assistant autonomy to `suggest` in Configuration → the button is absent;
   flip back. Click → the honest offline sentence.
4. The registry shows the model field with its `claude-sonnet-5` default.

**The key-day checklist** (the report's handover — the user's manual step, never mine):
set `ANTHROPIC_API_KEY` in App Service → Configuration → Application settings; the app
restarts itself. Then: one assistant turn exercising the tool loop (a search, then a
proposal at `propose` autonomy); at `suggest`, confirm proposals are withheld (AXM-026's
recorded next action — closing it closes the record); Portfolio narration returns prose
grounded in the visible figures; a Discussion thread's suggestion round-trips into an
applied record and appears in History attributed to the person who applied it.

## The step carrying the most regression risk

**Step 2, the engine config.** It rewires the model id of the product's one live AI path.
Every client that posts a `ChatConfig` — including stale browser mirrors written before the
field existed — starts flowing through the new read, and the failure mode is total: a
missing fallback turns every assistant turn into an error the moment a key exists, in the
hands of whoever first tries the assistant on key-day, which is precisely the day everyone
is watching it. The guards: the `?? 'claude-sonnet-5'` chain at every use site, the offline
path's indifference to the field, and the palette scenarios holding at 186.

## Details most likely to be got wrong

1. `narrationFigures` builds in the BROWSER from the reader's boot state — never a server
   `loadWorkspace`, which has no reader to redact against.
2. E5A's sentinels are planted values asserted absent from the SERIALIZED payload — not
   field-name checks, which miss a value smuggled under another key.
3. The model id travels in the POSTED slice like autonomy does; `/api/chat` stays stateless.
4. Suggest-work sends only what the reader already renders — the messages `/api/discussion`
   returned, stubs excluded.
5. Apply goes through `applyProposal` — one apply path, not a second dispatch that would
   fork validation.
6. The autonomy gate reuses `assistantAutonomy`/`canPropose`; `'off'` already hides the
   assistant entirely via `assistantOffered` — no third check.
7. The no-key response is 200 + `offline: true` — a fact in words, never styled as an error.
8. `parseConfig`'s fail-closed philosophy extends to the model id: unknown → undefined →
   the default; never the most expensive model by accident.
9. E5B extends `validateCreate` only if a hostile case actually slips through — and then
   pins the new edge in the same scenario.
10. The narrate call's token cap mirrors the chat route's `MAX_TOKENS`, not something new.

## Commit boundaries

1. `lib/assist.ts` + E5A/E5B/E5C + `data/validation.json`.
2. Engine config (registry field + posted slice + route read with fallback) — alone,
   because it is the risk step and must be revertible in one motion.
3. `/api/assist`.
4. The two buttons.
5. Deploy is not a commit; the report closes with the key-day checklist.

## What would send the design back

- The registry cannot carry a model id without restructuring agent configuration — the
  field stays a constant until the registry grows up. Surfaces at step 2's first edit.
- `CreateProposal` cannot express a thread-drafted item without loosening `validateCreate`
  — stop; extending the gate is a deliberate act with E5B pinning it, and if the shapes
  truly diverge the feature needs its own gated shape, which reopens the design. Surfaces
  at step 3/4.
- The narration payload cannot stay useful while redaction-clean — the feature shrinks to
  what the reader may see; if that guts the narrative, the surface choice reopens. Surfaces
  while writing E5A.
