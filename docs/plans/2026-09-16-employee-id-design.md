# Employee ID — design

## What this is

Every person in the directory who is genuinely part of the Axiocloud team gets a visible,
sequential employee ID — something a firm's own HR and admin processes can refer to, distinct
from `Person.id` (the internal `PERSON_n` key nothing outside the database ever sees). Confirmed
scope, from three rounds of clarification on 2026-09-14/15:

- **Location-coded format deferred.** The original ask was an ID "strong to handle multiple
  country or location," but no location/country field exists anywhere on `Person` today, and
  assigning one to each current team member is real data entry nobody has done. Rather than
  guess or block on collecting ~21 locations now, this ships a plain sequential ID with no
  location segment. A location-coded scheme is a later, separate design once the data exists.
- **No import of existing numbers.** Confirmed nobody has a real, pre-existing employee number
  today — every ID is freshly generated by this feature, for everyone, with no reconciliation
  step.
- **Backfill is scoped to current internal team members** — not the whole directory, not new
  people only. Client-facing and guest roles ("Nishant (OAPIL Guest)," "Client Process Lead")
  are explicitly excluded.

## Format

`AX-####` — a fixed `AX` prefix, a zero-padded four-digit sequence, assigned in the order people
are recognised as team members (see below). `AX-0001`, `AX-0002`, ... One global counter, not
per-role or per-cohort.

Four digits is headroom, not a hard ceiling — `nextEmployeeId` (below) keeps working past 9999,
it just stops zero-padding to four places. Nothing about this format assumes a location; a
future location-coded scheme is a different prefix pattern for *new* assignments and does not
require rewriting IDs already handed out.

## Who is eligible

Not a hardcoded list of role ids. A person is eligible the moment any role they hold grants the
existing `internal.view` permission — the permission that already draws the internal/external
line everywhere else in this codebase (`lib/access.ts`'s own module comment: "the boundary is the
point"). Concretely, every role in `DELIVERY_CORE` (Engagement Lead, Principal, Project Manager,
Functional, Technical) carries it, `ROLE_SUPPORT` carries it explicitly, and `ROLE_ADMIN` carries
it via `ALL`. The three seeded client roles do not.

This is deliberately a permission check, not a role-id check: a firm that later adds a custom
internal role and grants it `internal.view` gets employee IDs for that role automatically,
without this feature needing to know the role exists. A custom role that does *not* carry
`internal.view` — which is expected to be true of "Nishant (OAPIL Guest)" and "Client Process
Lead," but is **stored config, not something this design can read from source** — is excluded
the same way. Per the I27 precedent (stored grants can drift from shipped defaults), the backfill
step verifies this directly against production before writing anything; see "Backfill" below.

## Where the ID comes from

No new permission, no new top-level `Action`, no `persist.ts` change. `upsertPerson` is an
existing `ConfigOp` (dispatched under the shared `{t:'config', op:{k:'upsertPerson',...}}`
action, gated on `config.manage`, persisted whole via `persist.ts`'s generic `case 'config':`).
The assignment is a pure side effect inside that reducer arm (`lib/workspace.ts`, `case
'upsertPerson':`, ~line 8938):

- If the person already has an `employeeId`, it is carried forward unchanged. Never reassigned,
  never revoked — a role change, a departure, anything else leaves it alone.
- If they don't, and the roles they hold **after this edit** (`person.roleIds`, already computed
  and filtered a few lines above) grant `internal.view`, they are assigned the next id.
- Otherwise no `employeeId` is set.

This makes assignment lazy and general: it fires for a brand-new hire created with an internal
role, for an existing person given one later, and for the one-off backfill below, through the
same code path — no separate "backfill mode."

`employeeId` is never read from `op`. It is derived only, so nothing lets a client-supplied value
overwrite it.

```ts
// lib/config.ts, alongside nextCareerOptionId
export function nextEmployeeId(people: Record<string, Person>): string {
  let max = 0
  for (const p of Object.values(people)) {
    const m = /^AX-(\d+)$/.exec(p.employeeId ?? '')
    if (m) max = Math.max(max, Number(m[1]))
  }
  const n = max + 1
  return `AX-${n < 10000 ? String(n).padStart(4, '0') : String(n)}`
}
```

```ts
// lib/access.ts — the roster-in-hand version of permissionsFor's question
export function rolesGrant(model: OperatingModel, roleIds: string[], key: PermissionKey): boolean {
  return roleIds.some((r) => (model.access.grants[r] ?? []).includes(key))
}
```

`rolesGrant` reads `model.access.grants` directly — the same **stored** grants `permissionsFor`
reads, not `DEFAULT_GRANTS` — so it is automatically correct for whatever a tenant has actually
configured, including a role this design has never heard of.

## Backfill

A one-off script, run once against production after deploy — the same shape as the earlier
one-off script that seeded career data for four people (referenced in `persist.ts`'s
`updateCareerProfile` comment). Not a UI feature, not a new action.

The script:
1. Reads the live model, lists every person with `status !== 'Departed'` whose current
   `roleIds` satisfy `rolesGrant(model, roleIds, 'internal.view')` and who has no `employeeId`.
2. **Prints that candidate list — name, roles, resolved eligibility — before writing anything.**
   This is the live check the design above can't do from source: confirms that "Nishant (OAPIL
   Guest)" and "Client Process Lead" are genuinely absent from the list, and that the seven
   expected internal roles are genuinely present, against what production actually has stored
   today rather than what `DEFAULT_GRANTS` says it should have. Any mismatch stops the script
   short of writing, for a human decision, not a silent workaround.
3. Sorts the confirmed candidates by `joinedOn` ascending (undated people last, then by name), so
   the backfill hands out low numbers in roughly the order people actually joined.
4. For each, dispatches `{t:'config', op:{k:'upsertPerson', id, name, roleIds}}` — **`roleIds`
   copied exactly as-is**, because that field has no carry-forward in the reducer
   (`roleIds: op.roleIds.filter(...)`, no `existing` fallback — the one field in that object
   literal that isn't absent-means-unchanged). Omitting it, or sending `[]`, would strip the
   person's roles and fire a "Your record changed" notification to them as a side effect.
   `grade`/`track`/`developingToward` are left out of the op entirely (not sent as empty
   strings) — `career()` only overwrites a field when `op` explicitly sends it, so omitting
   them is what preserves the career data added earlier this week.
5. Each dispatch triggers the same lazy-assignment logic as any other edit, minting the next
   `AX-####` in order.

## Display

- **People list** (`components/capacity/PeopleDirectory.tsx`): a new `ID` column, monospace like the
  existing `Joined` column, showing `p.employeeId` or an em dash for anyone not yet assigned
  (client contacts, or an internal person somehow still mid-backfill).
- **Profile Overview** (`components/ProfilePanel.tsx`): a new read-only row using the existing
  `Fact` component with `editable={false}` always (not gated on `mayConfigure` or any
  permission — it is never editable by anyone, so there is nothing to gate) and
  `display={person.employeeId ?? '—'}`.

## What this doesn't do

- **No manual override or correction.** Once assigned, nobody can change an employee ID through
  the UI. Acceptable specifically because nothing is being imported — every id is freshly minted
  by this feature, so there is no "wrong on arrival" value to fix. If that changes (a real
  external numbering scheme shows up later), that is a new design, not a gap in this one.
- **No location segment**, per the scoping above — a later, separate design once location data
  exists on `Person`.
- **Resume-upload-to-profile** is the other half of the "new-people workflow" bucket this came
  from. Untouched, unscoped, and left for its own design cycle.
