# E5 — AI: the engine decision closed, and two features that never write

**Status: approved 2026-08-30** (five explicit decisions, recorded below).
Phase E5 — the final phase of the platform evolution
(`2026-08-29-work-platform-evolution-design.md`): "AI — conversation→work suggestion,
delivery-risk narration. Revisits the engine decision; the command-palette groundwork and the
dormant Claude path both carry forward as the substrate." E0–E4 are complete and live.

The parent design's non-goal is this phase's frame, verbatim: *"no AI that creates or
modifies work without a person applying it — the proposal-card contract already in force for
the assistant is the template for every future automation."*

## Decisions (settled with the user, 2026-08-30)

1. **Scope: the engine plus both vision features** — live-model assistant, thread→work
   suggestion, delivery-risk narration — in one phase; each piece is small because the
   substrate exists.
2. **Narration surfaces on the Portfolio, on demand.** A button, not a scheduled note: zero
   tokens until asked, and an asking READER whose redactions scope the payload — the daily
   pass has no reader to redact against.
3. **Thread→work is person-initiated, per thread.** A button on a Discussion thread; no
   ambient watching, no unsolicited cards. Mail is not a source (intake already turns mail
   into work; the marginal case is thin).
4. **Model: `claude-sonnet-5` by default, configured in the agent registry** — the right
   cost/latency point for a product loop, with Opus one config change away. The hardcoded
   `claude-opus-5` constant retires.
5. **Approach: one thin sibling route with client-built payloads** (below). Rejected: typed
   chat commands (undiscoverable, conversation-shaped where these are button-shaped) and
   registry agents gaining runtimes (declared stays declared; out of scope).

**The credential constraint, stated:** activating the live path is the USER's one manual step
— `ANTHROPIC_API_KEY` in App Service settings, like the intake token. The assistant building
this phase never handles the key. Everything is built and live-verified against the offline
path; the model-path live checklist runs the day the key is set, which is also the day
AXM-026's recorded next action closes.

## The engine decision, closed

The live model is the assistant's engine whenever the key exists; the **offline command
palette is the permanent fallback**, not a temporary state — a deployment without a key is a
complete product. The model id lives in agent-registry configuration (default
`claude-sonnet-5`); `app/api/chat/route.ts`'s constant reads it. Autonomy enforcement stays
exactly as built: what the model is *given*, not what it is asked nicely.

## `/api/assist`

One new route, POST, two kinds — deliberately single-shot (no tool loop; that is the chat
route's job) and **stateless in the chat route's established posture: the client builds every
payload from the reader's own redacted state**, so the model can only ever see what the
asking person may see. Session-verified like `/api/workspace`; the no-key answer is honest
("The assistant is offline — no model key is configured") and the buttons render that state
rather than hiding.

- **`narrate`** — takes the figures payload, returns prose. No writes; the proposal contract
  does not even engage.
- **`suggest-work`** — takes a thread's messages plus scope context, returns a
  `CreateProposal`. The server sanity-checks the model's output exactly as the chat route
  does, and the client re-validates through the same pure gate in `lib/chat.ts` before any
  card renders — model output is untrusted input, checked twice by one rule.

## Narration on the Portfolio

A "Narrate this" button. The payload is a pure projection — `lib/assist.ts`: portfolio
concerns, forecast verdicts, health and overdue counts, availability headlines (E4 meetings
included) — built from the reader's redacted state and **scenario-pinned to contain no
rates, no leave reasons, and nothing `clientView` withholds**. The returned prose renders
inline under an "AI-written; the figures are the source" note.

## Thread→work on Discussions

A "Suggest a work item" button on a Discussion thread (issue and project scopes), present
only when the registry's assistant autonomy allows proposals (`propose` or above) — at
`suggest` the affordance is absent, the same withholding philosophy as the tool loop. The
model drafts title, description, work type and severity from the messages; the card shows
the draft; **Apply dispatches the ordinary `create`** under the right parent — a project
thread's project, or an issue thread's own parent — through full validation, History, and
attribution to the person who applied it. The non-goal holds by construction: the model
described a mutation; a person made it.

## Error handling

Model refusals and malformed outputs answer in words on the card/panel, never as broken UI;
the draft or figures stay visible. Rate/size caps mirror the chat route's (bounded payloads,
bounded history). A rejected key reports itself as the chat route already does.

## Testing

- **E5A** — the narration projection, built from a state carrying withheld rates and leave
  reasons, asserts their absence: the redaction-safety net for the one new thing the model
  gets shown.
- **E5B** — hostile model outputs (unknown status, forged extra fields, oversized text)
  bounce off the proposal gate before any card exists.
- **E5C** — the suggest-work request builder: message trimming, stub exclusion, caps in the
  spirit of `MAX_INDEX_ROWS`.
- No new reducer arms, so no persistSteps work and no new persistence-proof surface. The
  route is thin; the pure parts carry the proofs.
- Live: offline-mode behaviors and both buttons' honest no-key states now; the model-path
  checklist (tool loop, suggest-withholding, narration quality, thread→work end-to-end)
  runs the day the key is set.

## Non-goals

Automatic or ambient suggestions, mail-source suggestion, scheduled narration, any write a
person did not apply, registry agents gaining runtimes, streaming responses (single-shot
answers render whole).

## What would send this design back

- If the registry cannot carry a model id without restructuring how agents are configured —
  the "config not constant" premise fails and the model stays a constant until the registry
  grows up. Surfaces at the first engine step.
- If `CreateProposal` cannot express a thread-drafted item without new fields the validation
  gate does not know — widening the gate for the feature would loosen the one check that
  makes model output safe; stop and extend the gate deliberately, with E5B pinning the new
  edges. Surfaces at the suggest-work step.
- If the narration payload cannot stay useful while staying redaction-clean (the story needs
  a number the reader may not see), the feature shrinks to what the reader may see rather
  than the payload widening. That is a scope answer, not a redesign — but if it guts the
  narrative entirely, the surface choice reopens. Surfaces in E5A's writing.
